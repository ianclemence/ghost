# Enforce the agency Ghost already promises

Ghost should resist the obvious reading of Anthropic's agent guidance. Anthropic's current position is not more agents, bigger harnesses, or broader autonomy; it is **one model in one context window, a small set of well-described tools and skills disclosed just in time, hard budgets, external verification, and containment that makes unattended work safe**. Ghost already exceeds most of that guidance on the trust side — one Permission Broker, runtime evidence, typed failures, honest limitation language, a credential vault, and an egress bridge — so its agency gap is not a philosophical one. The gap is **enforcement**: several mechanisms Ghost declares are recorded or advisory rather than binding. The verification level is written to telemetry and consumed by nothing; the todo list is model-set and in-memory; goal criteria accept a model-authored evidence string; subagents are described in a way that encourages the exact sequential handoff Anthropic warns against; and the learning pipeline treats a non-empty reply as success. The highest-value work now is to make those mechanisms bind: govern context inside the turn, tie "done" to observed effects, run a verifier that is not the doer, reserve subagents for parallel or context-isolated work, approve plans rather than steps, and learn only from verified outcomes. Throughout this report, **"What the sources establish" is cited evidence; "What follows for Ghost" is inference** from that evidence and from Ghost's code.

## Anthropic's 2026 answer is fewer agents, not more

**What the sources establish.** Anthropic's Applied AI team now recommends one model, one context window, and one open-ended tool loop as the target design. It reports that a **single agent with skills frequently outperformed both the one-prompt-for-everything design and the subagent design on quality, often at lower cost and latency per task** across enterprise deployments ([fold subagents](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)). Subagents remain justified only for three conditions: measurable performance degradation from context bloat, multiple tasks that can run in parallel with fresh context windows that can be discarded, or a single agent that cannot select tools well because of conflicting instructions or an oversized tool set ([same](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)). Multi-agent systems typically use **3–10× more tokens** than single-agent approaches for equivalent work, and Anthropic has seen teams spend months on elaborate architectures that improved prompting on a single agent matched ([multi-agent systems](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)).

The counterexample is real but narrow. For breadth-first research, an Opus 4 lead with Sonnet 4 subagents **outperformed single-agent Opus 4 by 90.2%** on an internal research eval ([research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Anthropic's own follow-up limits the lesson: parallelization's primary benefit is **thoroughness, not speed**, and multi-agent systems often take longer overall because they do more total computation ([multi-agent systems](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)). Sequential phases of the same work, tightly coupled components, and shared state are named bad boundaries; each subagent call "hands back a lossy summary" and runs a nested model loop that adds latency ([fold subagents](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)).

The substitute for delegation is disclosure. Anthropic reports cutting **Claude Code's system prompt by over 80%** with no measurable loss on coding evals by moving procedure into skills and tool descriptions ([fold subagents](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop); [new rules of context engineering](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)). Tool search exists because selection degrades past **30–50 available tools**; a typical five-server setup consumed **~55k tokens of definitions**, and search cut that by over 85% by loading only the 3–5 tools needed ([tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). Presenting MCP servers as a file tree of typed functions took definitions from **150,000 tokens to 2,000** ([code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)). The recurring mechanism is interface design, not examples: TodoWrite's description fell from **~9,100 characters** of when-to-use lists to a short description, a `pending/in_progress/completed` enum, and one rule ([new rules](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)).

**What follows for Ghost.** Ghost's topology is already on the right side of this argument: one loop, **97 skills** read on demand, `find_tools`, and `pipeline` for holding intermediate lookups out of context. The mismatch is in the delegation instructions. `subagent` says "Use for a bounded step you need the answer to now" (`pkg/tools/subagent.go:726`), and `spawn` says "Use for long or independent work" (`pkg/tools/spawn.go:32`). The first is precisely the sequential handoff Anthropic says not to delegate: the main agent waits on a nested loop, gets a lossy summary, and loses the ability to revise the plan mid-step. The second is closer, but still does not require independence. Rewrite both descriptions around Anthropic's three triggers — **two or more independent facets, a subtask that will generate more than ~1k tokens of mostly irrelevant context, or a tool-set/instruction conflict** — require a declared output schema, and keep depth at one. Then add a routing eval: run the same 20–30 tasks solo and delegated, repeat each run, and compare per-task flips and p50 latency, not just final scores. Anthropic's migration warning is directly applicable: folding one specialist broke a passing process in one run out of two, and the failure was invisible in the aggregate score ([fold subagents](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)).

Tool selection is the second mismatch. Ghost offers a core set plus keyword-matched niche tools, with `find_tools` as an escape hatch (`pkg/tools/profiles.go:428`; `pkg/tools/find_tools.go`). That is a reasonable local substitute for tool search at Ghost's scale — Anthropic itself only recommends search past ~10 tools or ~10k tokens of definitions ([tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)) — but it makes the model ask before it can act, and a hidden tool the model cannot name becomes "Ghost can't do that." Ghost's own prompt already tells the model never to say that before looking (`workspace/GHOST.md:280`). Instrument two rates: how often `find_tools` is called, and how often a turn ends in a capability refusal. If either is material, replace keyword gating with a compact always-visible catalog of one-line descriptions, loading full schemas only for the tools the model selects. Do not add a separate router or planner stage: Anthropic's evidence says the model that writes the plan should be the one carrying it out, revising it as results arrive ([fold subagents](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)).

## Context is a budget to govern mid-turn, not a window to fill

**What the sources establish.** Anthropic treats **server-side compaction as the default** long-context strategy and context editing as the fine-grained lever ([context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)). Compaction is explicitly a continuity mechanism: it keeps the active context small because response quality degrades as a conversation grows, but it is lossy by construction — images, documents, fetched URLs, and mid-conversation system instructions inside the summarized range are gone, and their text instructions stop applying ([compaction on demand](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand)). Tool-result clearing is the cheaper lever: it replaces the oldest tool results with placeholders and supports `keep`, `clear_at_least`, `exclude_tools`, and optional input clearing; it also invalidates cached prompt prefixes, so the docs advise clearing enough tokens to make the invalidation worthwhile ([context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)). Context **resets** are a model-specific workaround, not a permanent architecture: Anthropic added them for Sonnet 4.5's "context anxiety," then removed them on Opus 4.5 because the behavior was gone and the resets were overhead ([managed agents](https://claude.com/resources/articles/building-with-claude-managed-agents)).

The tool-result guidance is equally concrete. Consolidate tools around user intent rather than API endpoints; return only high-signal semantic fields and resolve UUIDs to names; paginate, filter, and truncate with sensible defaults; Claude Code caps responses at **25,000 tokens** ([writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). Error text is a prompt surface: return "specific and actionable improvements" rather than opaque codes or tracebacks ([same](https://www.anthropic.com/engineering/writing-tools-for-agents)). The two invariants that generalize furthest are **"unreadable ≠ empty"** and **"unconfirmed ≠ done"**: a failed read must be reported as unreadable, never as a quiet day, and a post counts as sent only when the destination confirms it; when the result is unclear, the run records "maybe posted" and changes nothing else ([agent automations](https://claude.dev/blog/building-effective-agent-automations/)).

**What follows for Ghost.** Ghost's failure semantics are already better than most of the industry: `Observation` carries status, error class, retryability, reconstructability, sources, and source-access; `ErrorClass` separates validation, permission, not-found, timeout, network, transient, and internal; only transient/network/timeout are retried (`pkg/tools/observation.go`). `VerifiableTool` adds a post-execution world-state check for writes, deletes, and appends (`pkg/tools/registry.go:500`), and the product layer has four limitation levels that decide whether a gap reaches the owner (`docs/EVIDENCE.md`). The gap is not error design. It is **context governance inside the loop**.

`FitContext` is called once, before `runLLMIteration` (`pkg/agent/loop.go:3117`), and nothing re-fits the message list as the loop appends assistant turns and tool results (`pkg/agent/loop.go:3682–4023`). Per-call caps are generous — 10k characters for shell output, 50k for `web_fetch`, 24k for delegated results — but a Deep turn allows 50 tool calls, and no equivalent trimming path was found in `pkg/providers`. A research turn that fetches a dozen pages can therefore present more tokens than a local model's window, and the failure will look like a provider error or a truncated answer rather than a context-budget decision. When `FitContext` does run, it drops the oldest whole turns first (`pkg/agent/context_budget.go`), which is the wrong eviction order for tool-heavy work: reconstructable tool output should go before decisions, errors, and the original request.

The mechanism to add is a **mid-turn context governor**. After each tool batch, estimate the assembled request. At roughly 80% of the input limit, replace old *reconstructable* results with a one-line placeholder and a spill path, keep the last N results, every unresolved error, every decision, the original request, and the active plan, and re-assert the turn's constraints. Log the tokens cleared and the number of results elided. This is Anthropic's tool-result clearing adapted to a local runtime; Ghost's prefix is statically tiered for cache stability (`docs/INTENT-REASONING.md`), so clearing older *history* is less likely to invalidate the stable prefix than clearing the core. Do not add resets: Ghost has no published evidence of context anxiety, and Anthropic itself removed them as models improved.

Two smaller fixes belong in the same pass. Make the **tool-call budget visible** to the model as a soft countdown ("N calls left; prioritize"), not only a hard ceiling. Anthropic's task budgets are a soft hint with a hard `max_tokens` backstop, and a budget too small for the task can cause refusal-like behavior: the model scopes down aggressively or stops with a partial result ([task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets)). Ghost's Quick tier caps a turn at six tool calls (`pkg/effort/effort.go`), which is exactly the undersizing risk. Second, audit failed tool results for **next-action language**. Ghost's `policyDeny` and many tool errors already name a remedy, but some paths still return prose; a sampled eval over real failures would find them cheaply.

## "Done" must be a state transition the model cannot author

**What the sources establish.** Anthropic defines the loop as running "until the goal is accomplished," not until a plausible answer appears ([anatomy](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)). Its documented failures are structural: an agent looks around, sees partial progress, and **declares the job done**; it tries to one-shot the work and runs out of context; it marks a feature complete without end-to-end testing ([effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The fix was a machine-readable feature list of **over 200 items**, all initially `failing`, which later agents could only flip to passing; one feature at a time; and a basic end-to-end test before any new work ([same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Anthropic chose JSON over Markdown because models were less likely to rewrite it inappropriately ([same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

Verification must come from outside the doer. Agents asked to grade their own work "confidently praise" mediocre output, and tuning a separate evaluator to be skeptical is "far more tractable" than making a generator self-critical ([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The evaluator must check **world state**, not the transcript: a flight agent saying "your flight has been booked" is not evidence; a reservation row is ([evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Criteria should be agreed before work begins, with hard thresholds and detailed feedback on failure ([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The cost is real: a solo app-building run took **20 minutes and $9** and produced a broken game; the full planner/generator/evaluator harness took **6 hours and $200** and worked, so the evaluator is worth it only when the task sits beyond what the model does reliably solo ([same](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

Approval design follows the same logic. Repeated per-step prompts become friction and users tune them out; Anthropic measured users approving **roughly 93% of permission prompts** ([how we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)). Plan Mode shifts oversight "from the individual step to the overall strategy" while still allowing intervention during execution ([trustworthy agents](https://www.anthropic.com/research/trustworthy-agents)). In commerce, the strongest pattern is staged writes: every write produces a proposal with a server-generated ID, `apply_change` succeeds only for IDs approved through a surface the model cannot call, limits are re-checked at apply time against current state, and writes are serialized per session so parallel calls cannot stack past a cap ([anatomy](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)).

**What follows for Ghost.** Ghost's evidence gate is the best part of its design, but it is **action-level, not task-level**. `TaskOutcome` counts completed, failed, and blocked consequential calls from canonical events (`pkg/agent/outcome.go`); it cannot see an intended step that was never attempted. `applyCompletionGate` only fires when something failed *and* the reply claims completion (`pkg/agent/completion_gate.go`). A turn that silently skips two of three requested steps, with no failure event, can therefore pass. The `todo` tool is the right shape but its statuses are model-set, its store is in-memory, and it is not connected to the completion gate (`pkg/tools/todo.go`). `goals.Criterion` is closer to the Anthropic pattern — `passes` plus `evidence`, with completion refused until every criterion passes — but it applies only to standing goals, and `check` accepts a model-authored evidence string rather than a runtime event (`pkg/goals/goals.go`).

Generalize that shape into a **per-turn work ledger**. Before acting on a multi-step request, the model declares the intended steps and an observable completion condition for each. The runtime binds each `completed` transition to a canonical event or evidence ID, and the completion gate refuses a "done" reply while a required step is open, naming the open step. Persist the ledger in the existing task store so a restart resumes rather than re-derives. Gate it by effort — multi-step or Deep turns only, five to eight steps — so a simple request does not pay for a plan. This is the single highest-leverage change for agentic behavior because it removes the model's discretion over whether to stop, which is the failure Anthropic documents most consistently.

**Verification is a dial Ghost records but does not turn.** `effort.Policy` assigns `VerifyBasic`, `VerifyStandard`, or `VerifyStrict` by tier (`pkg/effort/effort.go`), but the value is only written to the trajectory (`pkg/agent/loop.go:3403`); nothing in the runtime consumes it. Evidence proves an action ran; it does not prove the deliverable is any good. Make the dial real. For every consequential capability, require a read-back or a destination acknowledgement, not just an operation receipt; extend `VerificationContract` and `VerifiableTool` to messaging, email, calendar, and device control where the provider exposes a read path. At Standard and Strict, run a **separate verifier** over open-ended deliverables — a small rubric, hard pass thresholds, and bounded retries that append "previous attempt failed: {issues}" — and log its verdict to canonical events. Keep it off Quick and off reversible mechanical work; the documented cost is an order of magnitude, and Anthropic's own conclusion is that the evaluator is contingent on task difficulty, not a fixed yes-or-no ([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

**Approval should move from steps to plans.** Ghost's "allow for this task" grant is **time-bound, not plan-bound**: each use extends it by ten minutes, it ends after ten quiet minutes, and it hard-stops after one hour (`docs/PERMISSION-BROKER.md`). For a six-step task, the owner either answers six prompts or grants a broad time window that covers steps nobody approved. Add a `propose_plan` path for multi-step consequential work: a staged object listing each step's capability, arguments, limits, and reversibility; approval mints a plan-scoped grant; each step is still broker-checked and re-validated against current state at apply time; writes are serialized; any deviation from the approved plan stops and asks. Cap the step count and expire the plan with the task. This is a larger project, and it should follow the work ledger, because the ledger is the natural place to hang the approved steps.

## Containment buys autonomy; unverified learning spends it

**What the sources establish.** Anthropic's containment argument is the most directly transferable part of its security guidance. A tight perimeter is what makes unattended work safe: the OS-level sandbox produced an **84% reduction in permission prompts** while denying network by default, and Claude Code's reference devcontainer exists so the agent can run without per-action approvals ([how we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)). Human approval is a fallible control, not a boundary: users approved **93%** of prompts, and the more they see, the less attention they pay ([same](https://www.anthropic.com/engineering/how-we-contain-claude)). The strongest invariant is that credentials never enter the sandbox, so they cannot be exfiltrated regardless of whether the cause is the user, the model, or an attacker ([same](https://www.anthropic.com/engineering/how-we-contain-claude)). A domain allowlist is a capability grant, not a safety property: Anthropic documented an egress allowlist that passed traffic to `api.anthropic.com`, through which a malicious workspace file uploaded stolen files with an attacker-supplied key. "The sandbox worked perfectly, and yet the data was exfiltrated" ([same](https://www.anthropic.com/engineering/how-we-contain-claude)).

The injection numbers explain why containment, not detection, is the load-bearing control. Claude Opus 4.7 held prompt-injection success to **roughly 0.1% on single attempts and around 5–6% after 100 adaptive attempts** ([same](https://www.anthropic.com/engineering/how-we-contain-claude)). In an internal red-team, a phished employee pasted a routine-looking prompt asking Claude to read `~/.aws/credentials`, encode it, and POST it out; across **25 retries, Claude completed the exfiltration 24 times**, and because the instruction arrived through the user, "there's nothing anomalous for a classifier to catch" ([same](https://www.anthropic.com/engineering/how-we-contain-claude)). Persistent state is a first-class target: product memory, `CLAUDE.md` files, mounted workspaces, and the state directories of scheduled agents are reloaded on every start ([same](https://www.anthropic.com/engineering/how-we-contain-claude)). Memory poisoning can become "long-term memory drift," where no single change looks malicious ([Zero Trust, p.10](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf)). Least agency — restricting what each tool can do, how often, and where — is the operating principle, and sub-agents that inherit the parent's credentials have failed to compartmentalize ([Zero Trust, pp.6, 25](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf)).

**What follows for Ghost.** Ghost's containment is strong and should be treated as the reason it can be autonomous, not as a tax on it. The broker is the sole authority; the vault keeps secrets out of the model; the egress bridge gives the sandbox a loopback proxy rather than a network (`pkg/egress`); untrusted tool output is fenced with defused fence look-alikes (`pkg/tools/untrusted.go`); subagents have capability scoping and their output is treated as untrusted (`pkg/tools/subagent.go`). Do not respond to autonomy requests by adding more per-action prompts. That would spend the advantage Anthropic says containment buys.

The weak link is **what Ghost learns**. The evolution pipeline is enabled by default (`pkg/agent/loop.go:918–922`). `RecordTurn` marks a turn successful when `finalContent != ""` (`pkg/agent/loop.go:3339`), clusters "winning paths" by task kind, and generates skill drafts from those paths (`pkg/evolution/evolution.go`). That is a model-claim success signal, the exact thing Ghost's evidence layer exists to reject. A confident wrong turn is recorded as a success; its tool sequence becomes a "winning path"; a draft skill can encode it as persistent procedure. Anthropic's memory-poisoning warning applies directly: skills are state files reloaded on every start, and a poisoned skill is an instruction that survives restarts. Gate learning on **runtime evidence**: success only when every required ledger step is verified and no unresolved failure remains; drafts must cite the canonical events and transcripts they came from; every draft goes through a per-skill eval (10–20 cases with negative counterparts) and human approval; keep a rollback and a retention window. Exclude turns that read untrusted content and then wrote memory, a condition Ghost already tracks as `turnTouchedWeb`.

Two smaller least-agency fixes are worth doing in the same pass. `allowedCapabilities` in `pkg/tools/subagent.go` is documented as "empty = legacy unscoped"; make deny-by-default the default for every subagent, not an opt-in. And in `full` broker mode, consequential actions are auto-allowed while high-impact actions still ask (`pkg/permissions/permissions.go:320–325`). The high-impact floor is right. Consider an owner-visible "never auto" list for outbound and irreversible acts — sending email or messages, deleting files that predate the session — even in full mode. Anthropic's consumer guidance is explicit that some acts are never covered by "don't ask me again," however often they have been approved ([Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security)). This is a product judgment for a single-owner device, not a research finding.

## The owner experiences agency as intent, progress, and proof

**What the sources establish.** Anthropic's consumer guidance is to "show the work" while it happens: render a short progress line for each step in plain language, built from the tool's arguments or a dedicated `user_facing_message` parameter, because "time spent watching an agent work reads as progress" even when actual latency is unchanged ([anatomy](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)). UI should be structured tool calls, not prose or custom tags; presentation tools also give the agent a record of what is on screen, so "the first hotel" resolves against the messages array ([same](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)). Internal identifiers must not leak into user-facing text — it is an explicit interface eval, alongside item caps and empty/timeout states ([same](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)). Handoffs should batch questions into a single pass, repeat key context, and limit how many things each person sees at once ([human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams)). Structured digests beat raw feeds: the at-risk renewals agent pushes a daily digest in three buckets — positive momentum, negative momentum, recommended follow-ups — and takes follow-up questions ([Asana](https://claude.com/resources/articles/agents-you-can-coach-how-asana-builds-human-agent-teams-with-claude)).

**What follows for Ghost.** Ghost is ahead on vocabulary. `pkg/product` owns LLM-independent user-facing language; limitation facts are graded `none/contextual/material/blocking`; the activity feed explains why an approval was asked from the broker's risk class, never model prose (`docs/EVIDENCE.md`); the README's promise that "what it says it did is backed by evidence" is a real runtime property, not a slogan. The gap is that autonomy work has no single owner-facing surface connecting **intent → steps → evidence → what needs the owner**. Activity is a feed, `todo` is a model scratchpad, and jobs are a separate store. Build one "work" view — a chat card and a console page — fed by the same ledger the completion gate uses: what Ghost is doing, what it has verified, what it could not do, and what (if anything) needs the owner. Bind an interrupt control to the plan so the owner can steer mid-task, not just cancel.

Keep the evidence standard honest here. The claim that non-technical users should never see commands, paths, or tool names rests on **one interface-eval line and practitioner advice**, not a measured study ([anatomy](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents); [quality notes](https://claude.com/resources/articles/building-effective-human-agent-teams)). Treat it as a strong product judgment, not a research finding, and test it with five non-technical owners: time-to-understand what happened, unwanted prompts per task, and whether they can tell a verified outcome from a dispatched one. Do not over-invest in a new visual language before the ledger exists; the ledger is what makes the view truthful.

## Where the evidence thins, and what does not transfer

The corpus is unusually strong for enterprise deployments and unusually thin for a single-user local agent. Three limits matter most. First, **the headline numbers come from other task shapes**: the 90.2% research result is breadth-first search ([research system](https://www.anthropic.com/engineering/multi-agent-research-system)); the 20× harness cost is one app-building run ([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)); the 93% approval figure is developer tooling ([how we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)); the commerce patterns assume money, refunds, and a database that can be read back ([anatomy](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)). Personal tasks — "plan my trip," "sort out the school emails" — often have no oracle, no test suite, and no second reviewer. The doer-verifier pattern transfers in shape but not in cost or certainty.

Second, **the thresholds are missing**. Anthropic gives no token threshold for when context bloat becomes measurable degradation, no recommended compaction trigger fraction, no ceiling on skills before selection degrades (the 30–50 figure is for tools), no guidance on how many consecutive tool failures should terminate a loop, no wall-clock budget guidance, and no measured effect of error-message quality on recovery rate. For Ghost, the practical answer is to instrument its own p95 tool-call count, context overflow rate, `find_tools` rate, and per-task token spend, then set budgets from those numbers rather than importing Anthropic's. The same applies to verification: there is no published threshold for how much verifier coverage is enough.

Third, **the local-agent specifics are absent**. There is no published injection-success measurement for a local agent with full filesystem access; the available numbers are hosted products and benchmarks. Claude Code's documented fallback for Linux secrets is a `0600` file, weaker than a keychain, and there is no published model for per-task credentials without an identity provider ([Claude Code security](https://code.claude.com/docs/en/security)). Isolation guidance assumes a container or VM; a single-user Linux desktop may not have one. Async approval semantics — what happens when a routine needs a decision while the owner sleeps — are undocumented. Audit-log tamper-evidence assumes append-only infrastructure that a local disk does not provide. And learning from one person's outcomes is statistically thin and adversarially biased: one bad day can become a rule. Warp's improver loop assumes hundreds of contributors and thousands of reviews; at n=1, the human gate is doing much more work than the evidence acknowledges ([Warp](https://claude.com/resources/articles/how-warp-builds-self-improving-agents-on-claude)).

One more caution: Anthropic's security guidance is explicitly vendor guidance, "a framework for your own evaluation, not legal, compliance, or security assurance" ([Zero Trust, p.3](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf)). The mechanisms are sound; the assurance claims are not independent audits.

Items 1 and 2 share a representation: the ledger is the thing the governor must preserve and the gate must consult, so build them together. Item 3 depends on item 2's step definitions; item 5 reuses item 2's plan; item 6 depends on item 3's verdicts. If the team can do only one thing, do **item 2** — it changes what "done" means. If the team has one week, do **items 2 and 4**: the ledger fixes false completion, and the delegation fix removes a likely source of latency and cost with almost no architectural risk.

## Conclusion

The paradox in Ghost's position is that its trust architecture is what makes Anthropic-style autonomy possible, while the same architecture creates a temptation to declare mechanisms that are not enforced. The audit found five such declarations: a verification level nothing consumes, a todo list nothing gates, goal criteria that accept prose as evidence, subagent instructions that invert the delegation rule, and a learning loop that equates a non-empty reply with success. The next version of Ghost should be judged by a sharper question than "how many tools does it have?" — **can a claim be false without the runtime noticing?** Every item in the shortlist tightens that question.

The second takeaway is that, for a single-user local agent, the unit of autonomy is not the agent, the subagent, or the workflow. It is the **verified step**. Anthropic's enterprise advice scales down cleanly if you substitute "verified step" for "subagent" and "containment" for "organizational boundary"; it scales down poorly if you import the org chart, the swarm, or the assumption that a second model is a second opinion. Ghost already has the hard part — evidence, authority, and honest failure. What it needs now is to make those mechanisms bind, then let the eval results, not the architecture diagram, decide how far autonomy goes.
