# Hand-drawn animation

Produce a film that feels drawn by hand in both its marks and its movement.
For character animation, default to whole-pose drawings, expressive strokes and
intentional exposure. Design the keys and breakdowns before any rig or texture.
A rig may guide construction and contacts; the final drawing must carry the pose.
Canvas 2D is the renderer; SVG path data may be used for authored shapes. No
Blender or video model is needed. WebGL is not a dependency. Deliver an HTML
film with its local modules and an offline MP4. Length and format follow the
brief; a short, finished action is the starting point for a longer film.

## Draw it in code

A drawing is a list of strokes and a stroke is a list of points, so **any drawing,
and therefore any frame, can be written as JavaScript.** That is how Ghost draws:

- **Animation, cartoon, motion video, flipbook, drawn character:** a film. Every
  frame is strokes generated by code. Never reach for an image model to make
  frames.
- **A drawing, sketch, illustration, poster, diagram, logo, scene or greeting
  card:** the same engine with one frame. `film new` with `template` `still` (a
  layered dusk scene with a filled, inked fox: read it once, it shows the method),
  read [drawing-in-code.md](references/drawing-in-code.md), replace the subject,
  then call `film` with `still`. The picture appears in the owner's chat. Code gives
  the owner something they can ask to change precisely ("thicker line, move the
  moon left"), at any size.
- **Generate an image (the `image_generate` tool) only when they ask for one:**
  "generate", "AI image", "photo of", a photographic or painterly look strokes
  cannot reach. If you are unsure, draw it in code and offer to generate one.

## How the work runs on the Pod

You work like an animator: draw, look, correct, then commit to the render.

| Need | Use |
|---|---|
| Start a project | `film` action `new` (copies the engine and a template to `films/<slug>/`) |
| Write or change the film | `write_file` / `edit_file` on `films/<slug>/<slug>.html` |
| Does it run? are frames blank? | `film` `check` after every edit |
| See it | `film` `preview` with `grid`, `strip` or `frames`, the picture comes back attached to the result: **look at it** and fix what is wrong |
| A drawing for the owner | `film` `still` (one frame, full size, shown in the chat) |
| The finished film | `film` `render` (background job; the owner is told when it is in their chat) |
| Photos for the doodle look | `film` `photo` (scale, cut a plain backdrop, register in `photos.js`) |
| Read the method | `read_file` on `skills/hand-drawn-animation/references/...` |

Facts about the Pod that shape the work:

- A film's page has **no network** and cannot load files by URL: no web fonts,
  no remote images, no `fetch`. Everything the film needs is in its folder.
  Photos are embedded as data URLs by the `photo` action.
- Fonts are the Pod's own. `HAND_FONT` falls back to `cursive`; for lettering
  that must look the same everywhere, draw it as strokes (`squiggleText`) or as
  path data.
- Previews are quick at `width` 960. Render at the film's own width for delivery.
  A simple pencil or ink film renders at about half real time at 1080p; a heavy
  one (print plates, sand, many layers) can take several times its running time.
  Say roughly how long it will take; do not wait on it.
- One render at a time, at most 180 s of film. Cut a longer film into parts.
- Everything is deterministic: the same frame number draws the same pixels, so
  you can preview any frame and trust it in the render.

## Spend your tool calls on drawing, not reading

A film takes about a dozen tool calls: `new`, read the film file once, write it,
`check`, `preview`, look, fix, `render`. **Reading everything first uses up the
turn before anything is drawn**, and a film that is never built helps nobody.

- Read this file (done), then the film file that `film new` created (the starter
  shows the whole method). `film new` also returns a cheat sheet of the engine's
  API, so do not open `core.js` (it is 80 KB) or the other engine files.
- Read **at most two** more files, only if the brief needs them, then start:
  a drawing, illustration or poster: [drawing-in-code.md](references/drawing-in-code.md);
  a drawn character: [redrawn-animation.md](references/redrawn-animation.md);
  a particular look: [style.md](references/style.md); sand, pop-up paper or
  drawings on photos: [sand.md](references/sand.md),
  [paper3d.md](references/paper3d.md) or [doodle.md](references/doodle.md).
- Read the rest only when you hit a specific problem the film needs solved:
  [motion.md](references/motion.md) (keys, spacing, contacts, camera),
  [studio.md](references/studio.md) (exposure tracks, stable strokes, IK),
  [architecture.md](references/architecture.md) (full API, pitfalls),
  [mixed-media.md](references/mixed-media.md) (a film that changes material),
  and [palettes.md](references/palettes.md), [scenes.md](references/scenes.md),
  [reference-films.md](references/reference-films.md) (optional palettes, scene
  devices and historical references, never mandatory structures).
- **Render early.** A render runs in the background and can be redone, so call
  `render` as soon as `check` is clean and one grid looks right, then keep
  refining and render again. A good film that was never rendered helps nobody, and
  running out of tool calls before the first render is the most common failure.
- **Write in large pieces.** Rewrite a section with one `write_file` or one
  `edit_file` that replaces a whole block; do not spend a tool call on each line.
- Never stop to ask permission once you have the brief. Make the call, say what
  you assumed in one sentence, and build.

## Workflow

1. Fill [brief-template.md](references/brief-template.md) in your head and keep
   the brief and beat sheet at the top of the film file. Infer routine choices;
   ask the owner only for missing decisions that materially affect the result
   (one short question, with choices). Specify the intended material and acting
   reference separately. Pick a primary aspect ratio (a phone story is 9:16,
   otherwise 16:9); alternate formats need composition review, not just a
   different canvas size.
2. `film new` with a title. The default `starter` template is a complete small
   film (a ball drawn as strokes by code, held on twos, squash and stretch) to
   replace; `sketchbook-bird` is the primary character study to learn from
   (read it with `read_file` before building a character). Add `modules`
   `sand` or `paper3d` if the brief needs them. The engine files beside the film
   (`core.js`, `studio.js`, `cels.js`, `materials.js`) are never edited per film.
3. Establish the drawing: silhouette, proportions, expressions, necessary views,
   line hierarchy, recognizable stroke gestures and a few material samples. Preview
   at delivery size and small (a `grid`). A material cannot rescue an unclear
   pose. Use designed curves and replacement drawings where simple primitives fail.
4. Plan the keys and breakdowns of the hardest action. Mark contacts, gaze,
   anticipation, weight transfer and reaction. Use enough controls to express it;
   there is no fixed part count or parameter limit. Build a finite exposure sheet
   of whole drawings. Use geometric inbetweens only for corresponding forms;
   redraw changed overlaps, head angles, compressed silhouettes and expressions.
   Establish timing without decorative textures first. Do not add springs to rigid or motor-driven motion.
5. Finish one representative production shot before building the whole film.
   Evaluate consecutive-frame strips and stills. Correct anatomy, spacing,
   contacts and line stability before adding more scenes.
6. Build the remaining shots using a beat sheet: start, duration, what the viewer
   notices, main action, camera and sound cue. Cuts, transitions, blueprint views,
   montages, anchors and sign-offs are artistic choices. Give each action time to
   read. When mixing materials, carry the character's action, position or a
   physical object across the change. A palette swap alone does not establish
   a new style; several impressive but disconnected shots do not establish a story.
7. Check, then look. Start with a `grid` of 24, then a `strip` ("48,12") around
   a fast action or contact, and `frames` for full-size detail. A contact sheet
   alone cannot pass motion QA: you cannot watch the film, so say so plainly when
   you report, and report what you saw in the strips. Then `render`.
8. Deliver: the MP4 and contact sheet arrive in the owner's chat; the source
   stays in `films/<slug>/` for changes. In one or two sentences say what the film
   is, its length, and the real limitations (for example: "the walk cycle is on
   twos, the sound is a simple synthesized score"). Never call a film
   studio-quality solely because its code or checklist passed; assess the actual
   result against the chosen visual reference.

When the owner asks for a change, edit the film file and render again: it is
code, so a change is a precise edit, not a new attempt.

## Production invariants

- `defineFilm` defaults to **24 fps**. A scene receives continuous `tau`; `i`
  remains the legacy 12 Hz index for `pulse`, `boil` and older clips. Use exposure
  tracks per action. Ones, twos, threes and held drawings are all valid.
- **Never read `W`, `H`, `CX` or `CY` at file scope.** Your script's top level runs
  before `defineFilm` sets the frame format, so those values are still a 1:1 frame:
  a drawing placed with `CX` there lands off-screen in 16:9. Author drawings in
  local units (origin where you like, say the middle of the floor) and place them
  inside the scene with `c.translate(CX, CY + …)`. Use `CX`, `CY`, `W`, `H` only
  inside scene functions.
- Separate camera timing, drawing exposure and root motion. Check their combined
  screen-space motion, especially in a tracking shot. Avoid quantizing twice.
- Randomness is seeded. Make strokes once per drawing, with stable semantic ids.
  A held drawing holds its marks too. Seed changes belong to a new drawing, not
  every output frame. In a deformation workflow, use stable rest-space marks. Specify
  whether a texture belongs to the paper, an object or the screen. A fixed seed
  does not prevent swimming if sampling positions or topology change.
- Each frame must reproduce after seeking in the same pinned runtime. Sand uses
  fixed-step simulation and bounded checkpoints. Font and browser differences
  can change pixels between machines; provide fonts or use path lettering when
  reproducibility matters. Allow fonts and photos to load before export.
- Preserve physical contacts until their planned release. IK clamps unreachable
  targets; check the returned error and fix the pose rather than stretching bones.
- Record sources/licences for external media. Use only assets permitted for the
  intended delivery. Optional SVG is path geometry, not automatic rigging.
- A long line needs a flat pressure curve (for example `[[0,.55],[.08,.95],[.92,.95],[1,.45]]`)
  or the default taper fades it to nothing at both ends.

## Quality gates

**Drawing:** clear silhouette; consistent proportions across views; controlled
outer/inner line weights; purposeful pressure, taper and gaps; no accidental
tangencies or broken joints. Avoid assembled oval limbs with a texture laid over
them. Clean curves and aligned fills remain valid for the selected medium, but
the default sketch should retain visible drawing gestures. Wobble,
misregistration and boil require a purpose.

**Framing:** the subject is the picture. It should fill about a quarter or more
of the frame's width (a boat or a character a tenth of the width reads as a speck
on a phone). Place it on a thirds line, not dead centre, and give it room to move
into. Use the whole frame: in 9:16 (1080x1920) build three depths from top to
bottom (far bank or sky, middle water or ground, near foreground) so no half of
the frame is blank paper; in 16:9 keep the horizon off the middle. Look at the
grid for empty areas and for anything clipped at an edge, and fix scale and
placement before refining marks.

**Exaggeration:** on a phone a timid action does not read. A hop clears at least one
body height; a squash on landing is a quarter to a third of the body; anticipation
(a crouch, a pull-back) is two to four frames before any big move; a fast move
stretches along its path and settles with a small overshoot. If a strip shows the
subject moving by less than about a tenth of the frame, push it further.

**Motion:** whole poses that feel redrawn, meaningful keys, readable breakdowns, deliberate spacing, convincing
weight and planted contacts. Inspect overshoot, camera tracking, topology changes
and fast movement frame by frame. Use a designed smear when
needed; legacy `smear()` makes a ghost trail, not a new drawing.

**Material:** ink hatching follows form; graphite respects pressure and tone;
riso plates register coherently; screen ink may be solid; doodles interact with
the photo. Avoid excessive grain, changing raster phase and unintended shimmer.
For mixed-media work, inspect the transitions as actions, not only a style board.
If weather drives the scene, its force should affect both setting and character.
If paper unfolds, show a compact starting state, the hinges and an attached base.

**Delivery:** no page errors, accidental blank frames, clipped action, stale
frames or unfinished final lettering. If a closing card is requested, let it
finish and hold long enough to read. The render verifies that the encoded video
decodes and matches the film's length; the contact sheet is how you check the
whole of it at a glance.

## Working examples

`assets/starter.html` is the `starter` template: a bouncing ball, every drawing
generated by code, on an exposure sheet. Start here for anything small.

`examples/sketchbook-bird.html` is the primary pencil/ink drawing study: nine
whole-body keys, assisted inbetweens, a replacement blink and an exposure sheet.
It is also a `new` template (`sketchbook-bird`). `examples/four-looks.html`,
`examples/fly-style.html` and `examples/one-year.html` show the ink, pencil, riso
and screen looks and a sand year; `examples/material-studies.html` shows
sand-displacement and page-curl close-ups; `examples/becoming-phoenix/` is a
complete 60-second film with original music that combines all five looks, sand
and paper projection through one story (study `inkScene` for a moving storm,
`ensurePrintedPage` for a print becoming a page, `unfoldPhoenix` for staggered
wing and tail opening; use the techniques that serve the new brief, not its shot
list). Earlier examples remain useful for particular scene devices; see the
references above.

```text
film new      project "Paper boat"  template starter|sketchbook-bird|…  modules ["sand"]
film check    project paper-boat
film preview  project paper-boat  grid 24          # the sheet comes back attached: look at it
film preview  project paper-boat  strip "58,24"    # consecutive frames around the hard action
film preview  project paper-boat  frames "0,37,74" # full-size PNGs
film still    project paper-boat  frame 40         # one frame, shown in the chat as a drawing
film render   project paper-boat  look pencil       # whole film to MP4 in the background
```

`ar` and `width` override the film's format only when supplied; `look`
(`ink|pencil|riso|screen|doodle`) is passed through to films that support it.
Each full render stages its own frames and replaces that film's outputs only
after the MP4 has encoded and decoded cleanly. `grid`, `strip` and `frames` are
preview modes and do not replace the MP4.
