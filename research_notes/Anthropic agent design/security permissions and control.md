# Anthropic guidance on agent security, permissions, and enterprise control

*Scope: Anthropic primary sources published through October 2026, read against the needs of a local, single-user personal agent ("Ghost"). Evidence and principles only; no implementation proposals. Where a claim is Anthropic's stated position rather than an independently verified fact, it is attributed as such.*

## What threat model should a local personal agent assume?

### Takeaway
A personal agent concentrates every agentic threat class in one process, and the dominant one is indirect prompt injection through the content it reads — plus the user as a direct injection vector. Anthropic's own position is that model-layer defenses are probabilistic, so the design must assume some injections succeed and bound what a successful injection can reach.

### Cited Findings
- Anthropic lists five properties that break traditional security models: agents "execute operations without human initiation or approval at each step," have tool access including MCP, interpret ambiguous instructions, persist context across sessions, and coordinate with other agents — [Zero Trust for AI Agents, p.6](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- "Traditional access controls won't prevent agents from misusing legitimate permissions" — the agent can stay inside its grants and still cause harm — [Zero Trust, p.3](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf); [article](https://claude.com/resources/articles/zero-trust-for-ai-agents).
- Anthropic's threat list, drawn from OWASP: prompt injection and instruction manipulation, tool and resource hijacking, identity and access privilege abuse, memory and context poisoning, and supply chain risks — [Zero Trust, p.9](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Indirect injection is "the more insidious threat": payloads arrive in web pages or email, "the user never sees the malicious payload," and "Microsoft Research confirms that LLMs cannot reliably distinguish between informational context and actionable instructions" — [Zero Trust, p.9](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Tool poisoning is real, not hypothetical: "The first documented in-the-wild malicious MCP server impersonated a legitimate email service and secretly copied all sent emails" — [Zero Trust, p.9](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Tool chaining defeats host-centric monitoring: because "every command executes through trusted binaries under valid credentials, host-centric monitoring sees no malware and the misuse goes undetected" — [Zero Trust, p.9](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- "Unscoped privilege inheritance" occurs when a high-privilege manager agent delegates without scoping; the "confused deputy problem is amplified when agents routinely coordinate and delegate" — [Zero Trust, p.10](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- "Memory-based privilege retention": agents cache credentials or keys for context reuse, then "pull cached secrets from a prior secure session," escalating across session boundaries — [Zero Trust, p.10](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Injecting "just 250 malicious documents" can backdoor LLMs from 600M to 13B parameters, and "these backdoors persist through safety training including supervised fine-tuning and RLHF" — [Zero Trust, p.10](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Memory poisoning persists across sessions and can become "long-term memory drift": summaries or peer-agent feedback "gradually shift stored knowledge or goal weighting," which is hard to detect because "no single change appears malicious" — [Zero Trust, pp.10–11](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- The user is themselves an injection vector. In an internal red-team, a phished employee pasted a routine-looking prompt that asked Claude to read `~/.aws/credentials`, encode it, and POST it out; "across 25 retries of that prompt, Claude completed the exfiltration 24 times" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Because the instruction arrived through the user, "there's nothing anomalous for a classifier to catch"; "the only defense that holds in this situation is the environment, specifically egress controls that block the POST regardless of intent and filesystem boundaries that keep ~/.aws out of reach" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Anthropic states the general limit plainly: "any probabilistic defense has a non-zero miss rate" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Even best-in-class model defenses degrade with repetition: Claude Opus 4.7 holds prompt-injection attack success to "roughly 0.1% on single attempts, and around 5–6% after 100 adaptive attempts" on Gray Swan's Agent Red Teaming benchmark — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Persistent agent state is now a first-class injection target: product memory, CLAUDE.md files, mounted workspaces, and "the state directories of scheduled and long-running agents" are "reloaded each time the agent starts" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Multi-agent designs add a trust-escalation vector: if a sub-agent's output is treated as higher-trust than raw tool results "because such output came from 'us,' a new vector for prompt injection is introduced" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Anthropic tests personal-agent safety with three task variants per routine: "an innocent version, one with injected instructions, and one that tempts the agent to do more than it was asked" — [Claude Duet Safety, Privacy, and Security](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Anthropic concedes its Duet safeguards "will occasionally miss something or flag a harmless message," which is why they sit alongside approval mechanisms — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).

### Inferences
- For a personal agent, the highest-value data channels — inbox, web, calendar, documents, chat — are exactly the injection channels. A threat model that treats "the user asked for this" as trusted input is unsound, because the request itself can be attacker-authored.
- The relevant question is not "can we detect injection?" but "what can a successful injection reach?" Detection reduces frequency; containment bounds consequence.
- Memory, config files, and scheduled-task state are persistent attack surface, not transient context. They deserve the same trust scrutiny as inbound web content.
- A single-attempt success rate near 0.1% is not reassuring for an always-on agent that may process thousands of untrusted items; the 100-attempt figure is the operationally relevant one.
- The three-variant eval structure (innocent / injected / over-eager) is a portable test-design principle and maps cleanly onto a personal agent's routine tasks.

### Gaps
- No published injection-success measurement for a local, single-user agent with full filesystem access; the available numbers are for hosted products and benchmark harnesses.
- No public data on the base rate of indirect injection in personal email/calendar versus web browsing.
- The Zero Trust guide is explicitly vendor guidance — "a framework for your own evaluation, not as legal, compliance, or security assurance" — not an audited standard ([Zero Trust, p.3](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf)).

## What does least privilege mean for an agent, and what is "least agency"?

### Takeaway
Scope at the level of individual tool verbs and resources, per task and per session, deny by default, with a distinct identity per agent so compartmentalization is real rather than nominal. The practical test is blast radius, not the number of permissions granted.

### Cited Findings
- Least privilege: "Grant only the minimum access necessary for a specific task… By constraining what each identity can access, organizations contain the blast radius of any single compromise" — [Zero Trust, p.4](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- "Least agency," a term Anthropic credits to OWASP, "extends least privilege to agentic applications… restricting what each agent tool can do, how often, and where. In practice: a database tool gets read-only queries, an email summarizer gets no send/delete rights, an API gets minimal CRUD operations" — [Zero Trust, p.6](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Blast radius is the budgeting unit: "An agent with read-only access to a single database has a small blast radius; an agent with administrative access to cloud infrastructure has an enormous one" — [Zero Trust, p.6](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Foundation posture is RBAC with deny-by-default: "Block all access not explicitly granted. Treat this as a starting posture, not a destination" — [Zero Trust, p.14](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Enterprise adds ABAC on "time, location, data sensitivity, and risk score," and continuous authorization that "evaluate[s] authorization at each action rather than session start" — [Zero Trust, pp.14–15](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- JIT/JEA grants access "only at moment of need," scoped to specific resources and durations, with automatic revocation "after task completion or timeout" — [Zero Trust, p.15](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Compartmentalization via multiple agents is recommended, with an explicit failure mode: "each agent should have a unique ID and its own access credentials. If you break it into multiple agents and provide them all the same credentials, you have failed to compartmentalize the risk" — [Zero Trust, p.25](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Isolation should be enforced at the receiving end: "every workload carries its own cryptographic identity, and each service accepts connections only from the specific callers its policy names." Network segmentation is "a backstop, not the primary boundary" — [Zero Trust, p.15](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Asana bounds an agent by both its own grants and the invoking human: "an agent's effective access is bounded by the permissions of the person who triggers it," which lets agents "have broad access to public content, while minimizing the risk of anyone accessing information the agent has learned in a private context" — [Agents you can coach](https://claude.com/resources/articles/agents-you-can-coach-how-asana-builds-human-agent-teams-with-claude).
- Asana makes scope a configuration choice: "You could choose to grant access to a specific set of projects versus everything, or a specific set of documents, or a combination of documents and apps" — [Agents you can coach](https://claude.com/resources/articles/agents-you-can-coach-how-asana-builds-human-agent-teams-with-claude).
- Anthropic's multiplayer-agent guidance deliberately prefers coarse boundaries over per-item sharing: "a small number of clear, workspace-level boundaries removes decision fatigue," because humans and agents "find it difficult to navigate the soft boundaries of per-item sharing" — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).
- Cowork exposes mount modes read-only, read-write, and read-write-no-delete, and lets admins set "mount-path allowlists in MDM settings" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Claude Code's sandbox allows reads, allows writes "inside the workspace," and denies network "by default" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- A documented caveat: the working-directory boundary "is a permission prompt, so a Bash command you approve can still write anywhere your user account can" — [Claude Code security docs](https://code.claude.com/docs/en/security).
- Sub-agents are not automatically down-scoped: Claude Code sub-agents "can have up to the same permissions levels as it has been originally assigned… essentially there is no difference" from the parent from an external access standpoint — [Zero Trust, p.28](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Enterprise Cowork adds "role-based access and spend controls" and per-user daily activity analytics — [Building AI agents for the enterprise, p.16](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/69f3af1f0b8ebe5cde42fcda_Claude-Building-AI-Agents-in-the-Enterpise-04302026_v2%20(1).pdf).

### Inferences
- Service-level scoping is too coarse for agents: one credential often spans harmless reads and destructive writes. The meaningful unit is the verb-plus-resource capability ("read mail," "send mail," "delete file"), not the integration.
- The on-behalf-of intersection model — effective access = agent scope ∩ triggering principal's rights — is a sound default for a personal agent and avoids the union-of-privileges failure. Asana's framing is the clearest published example.
- Broad read access can coexist with least privilege if write, destructive, and egress capabilities stay narrow. That is how Anthropic reconciles "ongoing broad access to information" with containment.
- Sub-agent inheritance is a hole in compartmentalization. If sub-agents are used to isolate untrusted content, they must be down-scoped relative to the parent, or the isolation is organizational fiction.
- Coarse workspace boundaries may be safer than fine-grained per-item prompts, because fine-grained sharing produces decision fatigue and inconsistent judgment. The security gain comes from a few hard edges, not many soft ones.

### Gaps
- No published model for issuing per-task credentials on a single-user local machine; JIT/JEA guidance assumes an identity provider and secrets infrastructure.
- Unclear how to bound "read everything the user can read" on a personal device without a workspace/mount boundary; Anthropic's examples all rely on an OS or VM boundary.
- Anthropic does not publish how Asana-style delegation caps behave when the agent has learned private context in a prior session (the memory-vs-permission interaction).

## Where should the security boundary live: model, user attention, or environment?

### Takeaway
Deterministic environment boundaries — sandbox, filesystem scope, egress control, credential separation — are the load-bearing control. Model-layer defenses and human approval are probabilistic supplements. Containment is also what purchases autonomy: a tight perimeter is the precondition for running unattended.

### Cited Findings
- Anthropic frames exactly two ways to cap blast radius: "supervise the agent's behavior via a human-in-the-loop" or "containment… we supervise what it's *able* to do by enforcing access boundaries through, for example, sandboxes, virtual machines, and egress controls" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- The human-in-the-loop approach is described as "fallible": "Our telemetry showed users approved roughly 93% of permission prompts. The more approvals a user sees, the less attention they pay to each" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Model defenses "shape only what the agent *tends* to do, not what it is theoretically capable of doing," and "protection in the model layer will never be 100% effective, which is why it can't stand alone" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- The strongest single invariant: "if credentials never enter the sandbox, they can't be exfiltrated, regardless of whether the cause is a user, a model finding a 'creative' path, or an attacker" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Containment substitutes for oversight: "A tight perimeter also means you can relax oversight. Claude Code's reference devcontainer exists precisely so that the agent can run unattended, without per-action approvals" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- The OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) produced "an 84% reduction in permission prompts" while denying network by default — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Anthropic's architecture for hosted agents is to "split the 'brain' from the 'hands'": "the harness, session state, and credentials live outside the sandbox on durable infrastructure, and the sandbox becomes just a tool the agent uses for execution." This is called "the easy first step" — [A new approach to agent security with Claude Managed Agents and NVIDIA](https://claude.com/resources/articles/giving-companies-more-control-over-their-ai-agents-with-nvidia).
- NVIDIA OpenShell enforces policy outside the agent: it "blocks everything unless a rule allows it," checks each tool, applies rules to "the files, network connections and data the agent accesses," and "logs every decision it allows or blocks" — [NVIDIA/OpenShell article](https://claude.com/resources/articles/giving-companies-more-control-over-their-ai-agents-with-nvidia).
- The recommended tuning loop is empirical: "start with narrow permissions, review the log, and use Claude to tighten the rules toward the least access a task needs," then use a policy prover to confirm reachability — [NVIDIA/OpenShell article](https://claude.com/resources/articles/giving-companies-more-control-over-their-ai-agents-with-nvidia).
- Zero Trust calls sandboxing "table stakes for any agent handling untrusted input," recommending restricted container capabilities, gVisor-style syscall filtering, limited mounts and network, and microVMs/hardware isolation at higher tiers — [Zero Trust, p.15](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- A hard-won failure: a `.claude/settings.json` hook in a cloned repo executed before the "Do you trust this folder?" prompt. The fix was to "defer parsing and execution of project-local configuration until after the user accepts the trust prompt," and the general rule: "treat project-open, config-load, and localhost listeners the way you'd treat any inbound request from the internet" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- A second failure: an egress allowlist passed traffic to `api.anthropic.com`, and a malicious workspace file used an attacker-supplied API key to upload stolen files through the Files API. "The sandbox worked perfectly, and yet the data was exfiltrated" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- The corrected mental model: an allowlist is "a capability grant. Every function reachable through any domain on an allowlist is now an attack surface." The fix was a proxy that only passes requests carrying the VM's own session token and rejects attacker-embedded keys — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Anthropic's meta-lesson: "Battle-tested hypervisors, syscall filters, and container runtimes have survived more adversarial attention than anything you'll build"; across its deployments, "the standard primitives held while our own work around them exposed flaws" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Isolation has a visibility cost: the same VM boundary that contains the agent also keeps EDR out; Anthropic's mitigation is pull-based OTLP export, which "is not the same as live monitoring" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).

### Inferences
- On a user's own machine, the default environment boundary is weak: the agent runs as the user, sees the home directory, and inherits ambient credentials. Anthropic's patterns all assume an explicit boundary (container, VM, mount set) rather than the host itself.
- Egress policy should be expressed as a capability (destination + operation + credential), not a domain. Domain allowlists fail open at the operation layer.
- Anything parsed before consent — repo config, hooks, plugin manifests, local listeners — is already inside the trust boundary and should be treated as hostile input.
- Custom glue (proxies, allowlists, wrappers) is the most likely failure point; prefer mature primitives and keep custom logic small and testable.
- Autonomy and isolation are coupled: the stronger the perimeter, the less the agent needs to interrupt the user. Investing in containment is how you avoid investing in approval fatigue.

### Gaps
- No published guidance for isolating a local agent when a full VM is impractical (e.g., a single-user Linux desktop with no hypervisor); Anthropic's examples assume macOS/Windows virtualization or a container runtime.
- No public threat model for local MCP servers that need host database access — Anthropic moved these outside the VM for auditability and dependency reasons, which re-expands the host boundary ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)).
- The policy-prover claim for OpenShell is Anthropic/NVIDIA marketing; no independent evaluation was found.

## How should tool authorization and prompt-injection boundaries be enforced?

### Takeaway
Default-deny tool allowlists per role, verb-level capability restrictions, parameter validation on both the agent and tool side, and enforcement outside the agent. Treat all tool output as untrusted even when the tool is trusted, and never let a sub-agent's output inherit trust merely because it came from "inside."

### Cited Findings
- Tool allow-listing: "maintain explicit lists of permitted tools per agent function… using our deny-by-default approach, reject invocations of unlisted tools." Control it "on two fronts": at the agent level and "outside the agent level, in case the agent or the agent environment is compromised" — [Zero Trust, pp.25–26](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Tool authentication must be identity-bound: "certificate-based authentication on an API interface, or short-lived tokens bound to the calling agent's identity. Static API keys are not acceptable for tool authentication, even at Foundation" — [Zero Trust, p.26](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Capability restrictions are per-verb: "An email tool might be restricted to reading, with send capability requiring separate authorization. A database tool might permit queries but prohibit schema changes" — [Zero Trust, p.26](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Parameter validation "can, and should, happen on both the agent side and the tool side"; Claude Code exposes a `PreToolUse` hook for the agent side — [Zero Trust, p.26](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Input isolation treats "all natural-language inputs as untrusted," including uploaded documents and retrieved content. Microsoft's spotlighting technique "reduces indirect injection attack success from over 50% to under 2%" by delimiting untrusted content — [Zero Trust, p.25](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Constitutional classifiers add a detection layer and "blocked 95% of jailbreak attempts in testing with minimal increase in over-refusal rates" — [Zero Trust, p.25](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- "Tool output is an attack surface even when the tool is trusted." A GitHub connector "can load a poisoned README straight into the model's context despite passing malware checks" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Tool calls should route through proxies that "enforce network and file policy and can inspect return values before they enter the model's context." The inspecting classifier "can be a small, fast model; it doesn't need to be the one doing the reasoning" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Remote tools are a different risk class than local ones: local is auditable and pinnable, but a remote tool "can change behavior at any point after you've approved it; your install-time trust decision may no longer apply" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- MCP supply-chain visibility is incomplete by construction: project-scoped servers live in `.mcp.json`, but other scopes and connectors are configured elsewhere, so "reviewing `.mcp.json` doesn't show every server a session can load." Anthropic "does not security-audit or manage any MCP server" — [Claude Code security docs](https://code.claude.com/docs/en/security).
- Network fetches deserve separate treatment: `curl`/`wget` are not auto-approved by default, and deny rules match the command "as written," so policy enforcement that does not depend on command text should use sandbox network isolation — [Claude Code security docs](https://code.claude.com/docs/en/security).
- WebFetch reduces raw-content exposure: "Claude receives that call's answer instead of the raw page" — [Claude Code security docs](https://code.claude.com/docs/en/security).
- Multi-agent trust must be explicit: agents "should verify the identity and authorization of other agents before accepting delegated tasks" and "implement authorization checks at each step… rather than trusting that the initiating agent had appropriate permissions" — [Zero Trust, p.28](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- But treating sub-agent output as more trustworthy is itself a vulnerability — the "trust escalation" problem — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Asana's model gives each agent the specific integrations its role needs (e.g., HubSpot or a document drive) and publishes those permissions on the agent's profile page — [Agents you can coach](https://claude.com/resources/articles/agents-you-can-coach-how-asana-builds-human-agent-teams-with-claude).

### Inferences
- Injection defense is a four-layer stack: reduce reachable capability, delimit untrusted content, inspect tool returns before they enter context, and verify what leaves. No single layer is sufficient.
- "Trusted tool" is not a security property of the data it returns. Trust should attach to the channel and the inspection applied, not the vendor's reputation.
- An MCP server is simultaneously a code dependency and an injection vector; reviewing its source addresses only the first. Remote servers that can change post-approval should be treated as untrusted by default or continuously re-verified.
- Sub-agent isolation helps only if the parent treats the sub-agent's output as data, not as instruction. Otherwise the design creates a laundered trust path.
- Deny rules that pattern-match command text are inherently incomplete; enforcement that survives adversarial command construction must sit below the text layer (sandbox/network policy).

### Gaps
- No published benchmark for tool-output classifiers in local, single-user agents; the spotlighting and classifier numbers are research results, not product guarantees.
- No guidance on how often remote MCP servers should be re-reviewed, or what a practical re-attestation cadence looks like.
- Anthropic does not publish a canonical "safe tool schema" or a way to verify that a third-party MCP server's behavior matches its manifest.

## How should credentials and secrets be handled?

### Takeaway
The agent should never possess a long-lived secret. Credentials should be per-agent, per-session, short-lived, injected by a proxy outside the agent's address space, and revocable independently of the user's account. Secrets must be kept out of context and memory, not merely redacted from output.

### Cited Findings
- "Static API keys and shared service-account passwords are among the first things an attacker with model-assisted code analysis will find; they are no longer a legitimate entry point, not even at Foundation." — [Zero Trust, p.14](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- On static keys with rotation: "Treat them as already-compromised." — [Zero Trust, p.27](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- "If you are running API keys with rotation policies today, treat it as a known gap rather than a legitimate Foundation posture. Rotating a credential that can be grepped out of a lockfile does not raise the cost to an AI-assisted attacker meaningfully." — [Zero Trust, p.14](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Baseline is short-lived, narrowly scoped tokens "issued by an identity provider," with expiration "measured in minutes," automatic refresh, and "Never embed credentials in code or configuration files" — [Zero Trust, p.14](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Per-agent credentials are mandatory: "Credentials should never appear in code or configuration files; inject them at runtime from secrets management systems that log access and support emergency revocation" — [Zero Trust, pp.27–28](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- JIT access means "an attacker finds no cached credentials to steal," with token lifetimes "measured in minutes rather than hours or days" — [Zero Trust, p.28](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Claude Code stores credentials in the OS credential store rather than config files; `apiKeyHelper` can fetch from an external vault at runtime — [Zero Trust, p.27](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf); on Linux, keys are stored "in a file with mode `0600`" — [Claude Code security docs](https://code.claude.com/docs/en/security).
- Duet's three principles include: "Claude Duet never sees your passwords, browser cookies, sign-in tokens, or other credentials," and it "can't save them to its memory" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Password flow: the form "encrypts it with a single-use key that exists only on our secure cloud browser machine, for that one single use. It passes the encrypted password unopened to the browser, which types it into the site." — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Token flow is the general pattern: "A placeholder for the credential sits there instead and a proxy outside that machine puts in the real value only as a request is made." — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Cowork: "Credentials stay in the host's keychain and never enter the guest machine"; the VM gets "a per-session scoped-down token" that "can be revoked independently of the user's" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Cloud sessions: GitHub credentials are "stored encrypted on Anthropic's servers and never enter the session VM"; the VM holds "a short-lived credential scoped to that session," and a proxy "attaches the GitHub credential on the server side" — [Claude Code security docs](https://code.claude.com/docs/en/security).
- Remote Control uses "multiple short-lived, narrowly scoped credentials, each limited to a specific purpose and expiring independently, to limit the blast radius of any single compromised credential" — [Claude Code security docs](https://code.claude.com/docs/en/security).
- Payments use a scoped instrument: "a one-time card from a wallet like Link from Stripe, limited to that merchant and amount… Your real card number isn't shared" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Duet's "Never share" tier covers "sign-in credentials, full card and bank account numbers, and government ID numbers," which it must not share "even if you ask" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Claude Code's auto-mode classifier explicitly blocks "Printing a live credential or token into the transcript or a file" — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- Memory-based privilege retention is a named threat: cached credentials let an attacker "pull cached secrets from a prior secure session" and escalate across session boundaries — [Zero Trust, p.10](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).

### Inferences
- Secret handling is a containment problem, not a redaction problem. The durable fix is that the secret is never in the agent's address space; redaction is a last line, not a control.
- Placeholder-plus-proxy is the generalizable pattern: the agent composes a request, and an out-of-process proxy attaches authority. It works for API tokens, cookies, and payment instruments alike.
- A secret the agent can read is a secret the agent can leak — into a message, a log, a memory write, or a tool argument. "Never print credentials" must therefore be enforced at output and at memory-write time.
- Scoped-down session tokens revocable independently of the user's account are the minimum viable agent identity; they also make incident response possible without locking the human out.
- "Never share even if asked" is a useful category for a personal agent: some data should be outside the space of user-authorizable actions, because coercion and injection both look like user requests.

### Gaps
- No published guidance for local secret storage on Linux systems without a keychain or TPM; Claude Code's documented fallback is a `0600` file, which is weaker than the keychain case.
- No detail on how a local proxy bootstraps trust with the agent, or how the placeholder is prevented from being resolved inside the agent's process.
- No public data on credential-leak rates through memory or transcripts for personal agents.

## What makes approval UX work rather than train users to click through?

### Takeaway
Approvals must be rare, consequential, and bound to a fully specified action whose description is generated outside the model. "Don't ask again" should be a scoped, expiring capability grant — never extended to irreversible, financial, outbound, or identity-creating acts. Fail closed when the automated check cannot decide.

### Cited Findings
- Approval fatigue is empirically severe: "users approved roughly 93% of permission prompts," and "the more approvals a user sees, the less attention they pay to each" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Duet's approval card shows "the action, the destination, and the content, including every recipient," then waits — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- The check that governs the action runs separately: it "assesses whether the action matches your intent" and "runs outside the model doing the work so instructions hidden in a page cannot affect the outcome." The accompanying figure states the property directly: "nothing the agent reads can answer the card" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Some acts remain off-limits even with approval: "trading securities, banking actions such as moving money between accounts, and accessing someone else's account" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Some acts are never covered by "don't ask me again," "however often you have approved them": "paying or sending money, deleting an order, or creating an account" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Anthropic explicitly calibrated cadence and treats over-asking as a safety bug: "Approval fatigue is a serious issue, because too many requests teach people to tap through them, sometimes without adequate consideration" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Auto mode's classifier blocks actions that "escalate beyond your request, target unrecognized infrastructure, or appear driven by hostile content Claude read," while explicit ask rules still force a prompt — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- The classifier's default block list is a concrete taxonomy of high-consequence acts, including: downloading and executing code (`curl | bash`), sending sensitive data to external endpoints, production deploys and migrations, mass deletion on cloud storage, granting IAM or repo permissions, modifying shared infrastructure, "Irreversibly destroying files that existed before the session," force push, destructive git resets, `terraform destroy`, writing to a secret manager, changing DNS or TLS, merging an unapproved PR, approving Claude's own PR, disabling CI checks, posting a command to automation, toggling production feature flags, opening a tunnel or reverse shell to the public internet, "Printing a live credential or token into the transcript or a file," and "Launching an autonomous agent loop that runs without human approval or a sandbox" — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- Anthropic is explicit that the classifier is not a guarantee: "Auto mode reduces permission prompts but does not guarantee safety. Use it for tasks where you trust the general direction, not as a replacement for review on sensitive operations." — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- Measured classifier tradeoff: catches "roughly 83% of overeager behaviors before they execute," with "roughly 0.4% of benign commands blocked" and "~17% of overeager actions get through" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude), including footnote 1.
- Some actions no mode auto-approves, even `bypassPermissions`: explicit ask rules, organization-set connector asks, tools requiring user interaction, critical-path `rm`/`rmdir`, cross-session messaging safeguards, and reads outside working directories when that setting is on — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- "Deny rules block in every mode, including `bypassPermissions`." — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- `dontAsk` mode is fail-closed by design: "anything that would prompt is denied" — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- When the server cannot return a safety verdict, "Claude Code denies the action rather than run it unreviewed" — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- Approvals granted for "ask"-configured tools are "session-scoped and expire when the session ends" — [Zero Trust, p.27](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Approval decisions should be logged "for later explainability and justification," because "you need to perform forensics" — [Zero Trust, p.27](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Experienced users behave differently: they "auto-approve roughly twice as often as new users, but they also interrupt the agent mid-execution more frequently… supervising the agent only when it goes off track" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Match oversight design to user expertise: "The question of whether a user can evaluate what an agent is about to do should help determine the containment strategy," and getting it wrong in either direction is "its own failure" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Anthropic's own warning that per-action judgment does not transfer to non-developers: a knowledge worker "shouldn't be expected to judge bash incantations such as `find . -name "*.tmp" -exec rm {} \;`" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Asana keeps humans on the consequential decision: agents populate the unplanned board, but "people decide what moves from that board into the cycle" — [Agents you can coach](https://claude.com/resources/articles/agents-you-can-coach-how-asana-builds-human-agent-teams-with-claude).
- Human attention is treated as scarce: agents should "batch questions to be answered in a single pass… and limit how many things each human sees at once" — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).

### Inferences
- The right split is by consequence class, not by tool: auto-allow reversible, in-boundary actions; gate irreversible, outbound, financial, privilege-changing, and identity-creating acts.
- Approval text should be rendered from structured tool arguments, not from model-authored prose. A persuasive model can misdescribe its own action; the card must not depend on it.
- "Don't ask again" should be scoped to the exact capability (verb + resource + destination) and expire with the task or session. Standing, unbounded grants are how approval systems decay into rubber stamps.
- Fail-closed on classifier error is a UX requirement as much as a security one: silently executing when the check is unavailable teaches users that approval is theater.
- For a non-expert personal-agent user, per-action technical judgment is not a viable control. The approval surface should present outcomes ("send this email to these people," "delete these files") rather than mechanisms.
- A 17% miss rate on over-eager actions is acceptable only as one layer inside a sandbox; it is not acceptable as the sole gate for irreversible acts.

### Gaps
- No published threshold for "too many" approvals, and no public Duet calibration data (request volume, approval rates, time-to-decision).
- No data on approval fatigue for single-user personal agents; the 93% figure comes from developer tooling.
- Anthropic does not publish how the Duet intent classifier handles ambiguous user intent, or its false-positive rate in production.

## What should agent identity and audit trails contain?

### Takeaway
Each agent instance needs a cryptographic identity that appears in every request and every log, and each action needs a traceable chain from trigger to tool call to approval decision. Logs must be append-only and outside the agent's write scope, and must record "on whose behalf" as well as "which agent."

### Cited Findings
- Identity is foundational: "Without verifiable identity, you cannot enforce access controls, maintain audit trails, or attribute actions to specific agents" — [Zero Trust, p.13](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Foundation requires "persistent agent IDs backed by cryptographic material (not just labels)," tracked "from creation through retirement," appearing "in all logs and access requests" — [Zero Trust, p.14](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- "Unique identifiers alone are a labeling exercise; the Foundation tier now requires those identifiers to be cryptographically rooted so that identity forgery is actually hard." — [Zero Trust, p.14](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Higher tiers add X.509 certificates with rotation/revocation, mutual TLS with certificate pinning, and HSM/TPM-bound credentials with remote attestation — [Zero Trust, p.14](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Action logging should capture "all tool invocations, data access, and external communications," including "agent identity, timestamps and context" — [Zero Trust, p.15](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Enterprise-grade logs are "append-only storage" with "cryptographic verification of log integrity" and replication "to prevent single-point tampering" — [Zero Trust, p.16](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Traceability is separate from logging: it "connects those actions into complete sequences, linking each agent decision back to the original triggering event" — [Zero Trust, p.16](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Foundation traceability is a request ID "propagated through all resulting agent actions"; Enterprise is OpenTelemetry distributed tracing; Advanced is "full provenance chains" including "retrieved context, tool outputs, and reasoning steps," with replay — [Zero Trust, p.16](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Claude Code's implementation attaches "a unique `session.id` to each session, with `user.account_uuid` and `organization.id` attribution on all telemetry events" — [Zero Trust, p.24](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Sub-agent activity is distinguishable in telemetry and JSONL transcripts even when permissions are inherited — [Zero Trust, p.28](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Asana's design goal is a "distinct identity for every agent so its contributions and access can be audited, and a durable record of what agents can learn" — [Agents you can coach](https://claude.com/resources/articles/agents-you-can-coach-how-asana-builds-human-agent-teams-with-claude).
- Asana makes agent work visible and attributable: "when a task is assigned to an AI teammate everyone can see that an agent is doing it, and what it does. The agent posts activity, including its research plan and the steps it took" — [Agents you can coach](https://claude.com/resources/articles/agents-you-can-coach-how-asana-builds-human-agent-teams-with-claude).
- Enterprise auditability is framed as "visibility into what Claude is doing, when, and on whose behalf," delivered through OpenTelemetry-compatible tooling and used as an "evidence chain" for regulators — [Building AI agents for the enterprise, p.16](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/69f3af1f0b8ebe5cde42fcda_Claude-Building-AI-Agents-in-the-Enterpise-04302026_v2%20(1).pdf).
- Two metrics matter before any detection investment: dwell time ("how long between an anomaly occurring and a human becoming aware of it") and coverage ("the fraction of alerts that actually get investigated") — [Zero Trust, p.16](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- The operational test: "would we know within an hour if an agent went rogue?" with a target of detection "within an hour for critical systems" — [Zero Trust, p.30](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Settings changes should themselves be audited or blocked via `ConfigChange` hooks — [Zero Trust, p.16](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf); [Claude Code security docs](https://code.claude.com/docs/en/security).
- Isolation reduces audit visibility: VM-level containment kept EDR out, and pull-based OTLP export "is not the same as live monitoring" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Agent identity is explicitly unresolved at the industry level: "Should an agent possess its own principal identity, or should it act as an extension of the user and inherit the user's permissions? Ultimately, the answer may be a blend of the two." — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Duet gives users a task-level audit surface: a task list where "each task has its own page," with the ability to "steer it mid-task" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).

### Inferences
- The minimum viable audit record is: agent identity, session/task ID, triggering request ID, tool + verb + arguments, resource, decision path (auto/approved/denied), approver identity, egress destination, result, and timestamp.
- Logs must live outside the agent's writable scope. An agent that can edit its own audit trail has no audit trail, even if logging is "enabled."
- "On whose behalf" is a separate field from "which agent." For personal agents the delegating principal is usually one human, but recording it preserves the option to delegate and makes incidents attributable.
- Config changes are security events, not housekeeping; they should be versioned, reviewed, and alerted on like code.
- Visibility is in tension with isolation. A design that seals the agent tightly must budget for out-of-band export, or it trades auditability for containment.
- Agent work should be visibly agent work. Human reviewers need to know a non-human produced an artifact before they rely on it.

### Gaps
- No cross-platform agent identity standard exists yet; Anthropic points to NIST's project on AI agent identity and authorization and the six-agency agentic AI guidance, but does not adopt a scheme ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)).
- No guidance on tamper-evident local logs without a server or append-only medium; the Enterprise recommendation assumes infrastructure.
- No retention benchmark for personal-agent audit data. Claude Code's documented defaults are "30 days" server-side for enterprise deployments and a configurable local `cleanupPeriodDays` — [Zero Trust, p.29](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Anthropic does not publish how to reconcile "agent as principal" with "agent as user extension" for a single-user local agent; this is acknowledged as open.

## How much autonomy can an agent have without weakening the boundaries?

### Takeaway
Autonomy should be earned per task type and paid for with containment and verification, not with broader permissions or fewer boundaries. The strongest formulation in Anthropic's material is that autonomy is proportional to demonstrated reliability *and* to the strength of the perimeter; a tight sandbox is what makes unattended work safe.

### Cited Findings
- "Teams at Anthropic grant agents autonomy in proportion to demonstrated reliability, then expand it deliberately." Engineers have dispatched agents on "500 bug fixes independently," but "things certainly didn't start off that way" — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).
- Expansion is tracked per task type: "Tracking which kinds of tasks each agent has earned autonomy on and expanding scope per task type after repeated successes" — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).
- Verification is the precondition for autonomy: "the best long-running agents have many different ways to verify their work before a human looks at it," using tests, rubrics, and style guides — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).
- A doer-verifier split is recommended: "give one agent the job of doing the task and another agent the job of checking the first agent's work" — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).
- Human attention is the constrained resource: agents should "batch questions to be answered in a single pass, repeat key context… and limit how many things each human sees at once" — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).
- Guardrails can outlive their usefulness: "guardrails that used to be helpful may constrain a smarter model from pursuing more creative solutions" — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).
- Proactivity needs an explicit north star and an explicit allowlist: humans set the goal, then "choose which agents should proactively suggest new workstreams," because "it's unlikely that every agent on the team will have the prerequisite skills and trust" — [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams).
- Containment is the enabler of unattended operation: "A tight perimeter also means you can relax oversight… so that the agent can run unattended, without per-action approvals" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude).
- Auto mode deliberately nudges the agent to keep working: it "nudges Claude to keep working without stopping for clarifying questions, though Claude still asks when your prompt or a skill explicitly relies on it" — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
- Scheduled/away routines inherit the same safeguards rather than a lighter regime: "The routines that run while you are away have the same safeguards" — [Duet](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security).
- Asana keeps the consequential allocation human: agents populate the backlog, "people decide what moves from that board into the cycle," and tickets can be assigned to a person or a coding agent — [Agents you can coach](https://claude.com/resources/articles/agents-you-can-coach-how-asana-builds-human-agent-teams-with-claude).
- During incidents, Anthropic's rule is to "automate the bookkeeping around incidents, not the decisions. Models should take notes, capture artifacts… Humans should make the containment calls, the disclosure calls, and the customer-comms calls." — [Zero Trust, p.17](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Escalation thresholds are explicitly a balance: "Define thresholds that balance security against operational efficiency" — [Zero Trust, p.25](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a1611a04085d7cd3dadc924_Claude-eBook-Zero-Trust-for-AI-Agents-05182026.pdf).
- Anthropic's enterprise framing is that employees "set goals, delegate work, and receive finished deliverables," with output going "beyond drafts and suggestions to actual completed work" — [Building AI agents for the enterprise, p.15](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/69f3af1f0b8ebe5cde42fcda_Claude-Building-AI-Agents-in-the-Enterpise-04302026_v2%20(1).pdf).

### Inferences
- The autonomy equation is roughly: permissible autonomy ∝ containment strength × verification quality, not trust in the model's judgment. Improving either input buys autonomy; granting more permissions does not.
- Per-task-type autonomy ledgers are more useful than a single global "trust level," because reliability is domain-specific and does not transfer cleanly.
- Escalation quality is the real bottleneck for finished work. An agent that batches, ranks, and contextualizes decisions preserves human attention; one that asks constantly burns it and gets rubber-stamped.
- "Enough autonomy to finish" requires operating while the human is absent, which is only defensible when credentials are contained, egress is bounded, and irreversible acts are gated. Autonomy without containment is just unreviewed risk.
- Proactive work needs two explicit grants: a north star (what to optimize) and a scope (which agents may propose). Without both, proactivity becomes scope creep with a plausible rationale.
- Verification mechanisms are quality controls, not security controls; they should not be counted as injection defenses.

### Gaps
- No quantitative model for how much verification is sufficient per task class; the guidance is qualitative ("many different ways to verify").
- No public data on optimal cadence for expanding autonomy, or on how to detect that an agent's reliability has regressed after a model update.
- No measured effect of doer-verifier setups on prompt-injection resistance; Anthropic presents them as quality mechanisms, and the trust-escalation risk suggests they can even add a vector.

## Which enterprise controls transfer to a local personal agent?

### Takeaway
The transferable pattern is a centrally curated capability catalog, policy the agent cannot override, local execution, and out-of-band audit export. For a personal agent, the important analog is a reviewed, signed set of capabilities and a policy layer that the agent itself cannot edit — plus a deliberate separation between "using the agent" and "changing the agent."

- New internal plugins go through an approval workflow "before it reaches any employee's machine," which "transforms AI governance from a reactive exercise into a proactive one" — [Building AI agents for the enterprise, p.16](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/69f3af1f0b8ebe5cde42fcda_Claude-Building-AI-Agents-in-the-Enterpise-04302026_v2%20(1).pdf).
- Local execution is presented as a security feature: Cowork "processes your files, your data, and your documents on the employee's machine. ### Inferences
- For a local personal agent, "enterprise control" reduces to one question: who can change the agent's capabilities, and can the agent change them itself? The answer must be that the agent cannot.
- A reviewed, signed capability catalog is the local analog of a plugin marketplace. The review matters less for malware (containment handles that) than for *scope*: what the capability makes reachable.
- Separation of "user of the agent" from "admin of the agent" is valuable even for a single person, because it creates a deliberate, higher-friction mode for changing behavior — the same reason Asana separates working with an agent from training it.
- Local execution is a genuine security advantage for a personal agent, but only if the local machine is treated as the blast radius; "nothing is uploaded" does not mean "nothing can leave."
- Spend and rate limits address resource exhaustion and runaway loops, not exfiltration or destructive action. They should not be counted against the containment budget.
- The "impossible vs. tedious" test is the most portable single principle in the corpus: it distinguishes controls that survive a patient, cheap, automated attacker from those that merely slow one down.

### Gaps
- No published guidance for separating admin from user when both are the same person on the same machine; all examples assume an organization with distinct roles.
- No documented mechanism for signed local capability manifests outside Claude Code's managed-settings system.
- Anthropic does not quantify the security benefit of local execution versus self-hosted cloud execution for personal data; the claim is qualitative.
- The corpus contains no guidance specific to a local agent that must reconcile personal data across many services with no organizational boundary to lean on; the workspace-boundary advice assumes a team product.
